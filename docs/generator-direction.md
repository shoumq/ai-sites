# Универсальный генератор: JSON остаётся основой

## Решение

JSON — подходящая основа. Ограничение сейчас в его словаре и планировщике:
ИИ выбирает готовые секции, а многостраничный режим всегда раскладывает их
по четырём заранее заданным страницам. Удаление JSON лишит редактор
предсказуемых правок, валидации и одинакового превью/публикации.

Целевая цепочка:

**Профиль бизнеса → дизайн-бриф → план страниц → JSON-композиция → проверка → общий Vue-рендерер.**

Универсальность получается из сочетания контента, композиции и возможностей.
Профиль «кофейня» помогает начать, но не должен ограничивать человека
особым шаблоном кофейни. Сфера бизнеса остаётся свободным текстом.

## Что уже реализовано в этой итерации

- Новая студия создания сайта и рабочее пространство проектов.
- `BriefIn.preferences`: сфера, аудитория, тон, направление, нужные блоки,
  нежелательные приёмы. Старые запросы без `preferences` продолжают работать.
- Направления «Чистый», «Редакционный», «Выразительный», «Тёплый» компилируются
  в существующие оси темы и варианты hero. Новые типы сайта не требуются.
- Бизнес-контекст передаётся генераторам структуры, текста и изображений.
- Резервный генератор учитывает цель, несколько отраслевых подсказок и
  обязательные блоки. Это детерминированная сборка, а не языковая модель.
- Приоритет: ручная структура и оси → явно выбранное направление и функции
  → ответ модели → резервные значения. Ручная структура может исключать
  блоки, отмеченные на предыдущем шаге. Цвет бренда имеет приоритет над ИИ.
- Бриф сохраняется в `project.settings._generation_brief` обоими путями
  генерации (REST и WebSocket), сохраняется при обновлении настроек.
  Это внутренние данные проекта; публичный allowlist настроек их не экспортирует.
- Черновик мастера сохраняется в `sessionStorage` текущей вкладки.
  Это ещё не персональный профиль пользователя между устройствами.
- Правый эскиз показывает настроение, не обещает точное совпадение с результатом.
  Все настоящие блоки по-прежнему редактируются и публикуются через SiteSchema.

## Как развивать дальше

### 1. Явный план перед генерацией контента

Добавить валидируемый `SitePlan`: список страниц, назначение каждой,
секции, варианты, нужные действия и объяснение выбора. Показать человеку
план и дать менять его до дорогой генерации текста/медиа. Заменить фиксированную
`_build_multipage` компиляцией этого плана, проверять тарифный лимит страниц,
уникальные slug, внутренние ссылки, наличие выбранных возможностей.

### 2. Больше свободы внутри JSON

Добавить версионированный тип `composition` рядом с существующими блоками:
контейнер, сетка, вертикальная/горизонтальная группа, текст, изображение,
кнопка, карточка, ссылка на коллекцию. Использовать ограниченный набор
токенов, адаптивные правила и стабильные ID. Не заменять существующие секции.

Пример будущего контракта (это проектирование, ещё не поддерживается рендерером):

```json
{
  "type": "composition",
  "version": 1,
  "id": "intro",
  "layout": { "kind": "grid", "columns": { "mobile": 1, "desktop": 2 } },
  "children": [
    { "id": "headline", "kind": "text", "role": "heading", "text": "Дома для жизни" },
    { "id": "cover", "kind": "image", "asset_id": "brand-cover", "alt": "Готовый проект" }
  ]
}
```

ИИ выбирает композицию и токены; система гарантирует валидность, адаптивность
и редактирование. Ограничить глубину/количество узлов и разрешённые действия.
Произвольный JavaScript не нужен. Текущую sandbox-секцию с абсолютными координатами
не стоит делать основой обычных страниц: адаптивная сетка устойчивее.

### 3. Возможности бизнеса как отдельные модули

Реестр возможностей: каталог, заявки, корзина, расписание, бронирование,
личный кабинет, подписки. У каждой — схема данных, серверные операции,
права, нужные настройки и состояние подключения. Админка показывает
релевантные разделы по включённым возможностям проекта.

Галерея и форма — блоки. Бронирование слота и кабинет — серверные возможности.
Созданная форма записи сама по себе не управляет расписанием. Не давать модели
обещать функциональность, для которой нет подключённого модуля.

### 4. Предпочтения и обучение на выборе пользователя

Хранить отдельно профиль аккаунта, бренд-кит проекта и бриф конкретной
генерации. Приоритет: текущий запрос → настройки проекта → профиль аккаунта
→ отраслевые подсказки. Разрешить сохранить понравившееся оформление
как свой пресет и явно применить его к следующему проекту.

Начать с двух-трёх дизайн-планов и выбора пользователем. Записывать принятие,
отклонение и ручные правки. Это даёт данные о реальном вкусе; обучение модели
и векторная база на первом этапе не обязательны. Доступ к профилям и пресетам
должен быть ограничен владельцем/командой проекта.

### 5. Качество и воспроизводимость

Версия схемы, миграции старых сайтов, версии промптов, сохранённый план,
признак реального ИИ/резервной сборки. После генерации — проверка схемы,
ссылок, контраста, мобильной раскладки, обязательных функций и фактов.
Правки ИИ применять как проверяемый patch с undo, а не замену всего сайта.

## Текущие границы

Многостраничная сборка пока фиксированная; ручной набор работает внутри её
базовых страниц. Направления используют существующие шрифты и блоки, а не
неограниченную генерацию дизайна. Тон и свободные ограничения учитываются
в промптах реальной модели; mock не интерпретирует их семантически.
Выбранные функции сейчас означают соответствующие блоки; кабинеты и полноценное
расписание не реализованы. Персональные пресеты аккаунта — следующий этап.

Реальные YandexGPT/YandexART, база данных и публикация проверяются отдельно
в настроенном окружении. Локальная проверка этой итерации использует mock
провайдеров и браузерные API-фикстуры, не реальные аккаунты или оплату.
